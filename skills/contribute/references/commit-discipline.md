# Commit Discipline (steps 8-11)

Used in **Steps 8, 9, 10, 11** of the `contribute` pipeline. Read it before the first code change, then follow it while you work, not only at push time.

Core rule: **one logical change per commit, committed while you work.** Group files that only make sense together. Split work that a reviewer would want to accept or revert separately. If the whole fix is one idea in one or two files, keep it as one commit. Splitting for its own sake is noise.

## 1. What goes together, what stays separate

Put in the same commit:

- Fix plus its regression test. A fix without its test is incomplete, and a test without its fix proves nothing alone.
- Code plus the docs or comments that describe exactly that code. README or CHANGELOG lines belong with the behavior change they document.
- Rename or move plus its import and reference updates. The tree must build after every commit.

Put in separate commits:

- Fix versus unrelated cleanup, formatting, or refactor. Note the cleanup separately per SKILL.md step 8, do not fold it in.
- Two halves of an issue that can be reviewed apart (for example: behavior fix in one commit, follow-up docs or config sample in the next).
- Review-round fixes (step 10) versus the original implementation. Each round gets its own commit so the maintainer sees what changed after their comment.
- CI red fix (step 12) versus the original push. One small follow-up commit, never a silent amend after push.

Table for the common call:

| Situation | Commits |
|---|---|
| Typo, 1 to 5 lines, one file | 1 commit |
| One bug fix plus one test, one or two files | 1 commit |
| Fix plus docs or changelog that only that fix needs | 1 commit if tiny, else 2 (fix first, docs second) |
| Medium feature or multi-file fix with distinct parts | 2 to 3 commits, each building and passing its slice |
| Reviewer asked for changes, or CI is red | 1 new commit per round, no amend after push |

Never split one logical fix across many micro-commits (one file per commit, test apart from fix). Never dump three unrelated ideas into one commit because the diff is small.

## 2. Commit while you work, not once at the end

Steps 8 to 10 produce local commits. Step 11 pushes them. The order:

1. Implement one slice (step 8).
2. Run that slice's tests plus lint for touched files (step 9). Fix before committing.
3. Review the staging area (`git status --short`, `git diff --staged`). Stage only what belongs to this logical change. Use selective `git add <path>` over blanket add.
4. Commit locally with a message per section 3 below.
5. Repeat for the next slice. Run the full suite once before step 11, not only the last slice.
6. Step 10 review findings become new commits, one per round. Step 12 CI fixes become one follow-up commit.

Do not push until step 10 passes and the Voice Gate in step 11 passes. Local commits are cheap and reversible. A pushed mess is not.

## 3. Message format

Default to Conventional Commits unless step 5 found a repo convention that says otherwise:

```
<type>(<scope>): <short subject>

[optional body: why this slice, 1 to 3 short sentences]

[optional footer: Refs #N]
```

Types: `fix`, `feat`, `docs`, `test`, `refactor`, `chore`. Scope is the area when the repo uses it (for example `fix(router): ...`). Otherwise skip the parens.

Subject rules:

- One thing only. If it needs "and", it needs two commits.
- Present tense, lowercase after the colon, no period at the end.
- Keep to about 50 chars, hard max 72.
- Name the behavior, not the file. Good: `fix: reject empty --config instead of exiting 0`. Bad: `fix: update files` or `fix: comprehensive improvements`.

Body rules (public text, so `references/human-voice.md` applies):

- 1 to 3 short sentences: what broke from the outside, why this approach, what it does not cover.
- Plain B2 English, at least one contraction when over 2 sentences.
- Zero em dashes, zero en dashes as pauses, zero banned buzzwords. Backticked flags like `--config` are fine.
- Never add `Co-authored-by`, `Generated by`, or similar AI signature unless the repo CONTRIBUTING.md or PR template explicitly asks for it.

Footer: keep `Closes #N` for the PR description (per `references/pr-template.md`), not repeated in every commit. Commits may carry `Refs #N` when it helps `git log` readability. Never invent an issue number.

## 4. Pre-commit checklist (every commit)

Run these before each local commit:

```bash
git status --short
git diff --staged
# run the slice check, examples:
# JS: pnpm vitest run <touched> && pnpm eslint <touched>
# Go: go test ./<pkg>/... && go vet ./<pkg>/...
# Rust: cargo test -p <crate> && cargo clippy -p <crate> -- -D warnings
# Python: uv run pytest <touched> -q && uv run ruff check <touched>
# Docs/skills repos: run the repo validator when it exists (for example `python3 scripts/validate-skills.py`) plus a relative-link check
git config --get user.name
git config --get user.email
```

All must hold:

- [ ] Staged diff contains one logical change only. Unrelated hunks are unstaged.
- [ ] Slice tests and lint for touched files pass. Full suite passes before push (step 9).
- [ ] No secrets, tokens, `.env` content, or private URLs in the diff.
- [ ] Identity resolves to the real submitter. If not, stop and ask per SKILL.md step 11.4.
- [ ] Message follows section 3. Voice Gate Rule 6 passes on the message body.

If any box fails, fix it before committing. Do not commit red code to "fix later".

## 5. After push: new commits only

- Never amend or force-push after step 11 publishes the branch. Review replies and CI fixes are new commits on the same branch.
- Do not squash during review unless the maintainer asks. If they ask for squash at merge time, let the platform squash. Keep the branch history readable until then.
- Keep the branch to what the issue needs. Three clean commits beat one tangled commit and beat ten micro-commits.

## 6. Examples

Single commit (tiny fix, fix plus test travel together):

```
fix: reject empty --config instead of exiting 0

`--config ''` slipped through because the parser only checked
presence. I added the empty check next to the existing ones with
one table case. Doesn't cover missing file reads, happy to follow up.

Refs #241
```

Two commits (fix first, docs second):

```
1. fix: reject empty --config instead of exiting 0
2. docs: note empty --config error in CLI usage
```

Three commits (medium work, review round visible):

```
1. fix: reject empty --config instead of exiting 0
2. test: cover empty and whitespace --config cases
3. docs: note empty --config error in CLI usage
```

Bad splits to avoid: test committed apart from the fix it proves, formatting-only churn mixed into the fix, two issues sharing one commit message with "and".
